# MASAR API — Notifications

## Overview

The Notifications API manages user notifications generated by important events across the MASAR platform.

It covers:

* Listing notifications.
* Viewing a notification.
* Marking notifications as read.
* Marking all notifications as read.
* Unread counts.
* Deleting notifications.
* Notification types.
* Notification preferences where supported.

Base URL:

```text
/api/notifications
```

All notification endpoints require authentication.

---

# Authentication

Protected endpoints require:

```http
Authorization: Bearer ACCESS_TOKEN
Accept: application/json
```

The authenticated user is determined from the access token.

The client must never provide the recipient user ID as the authoritative identity.

---

# 1. List My Notifications

Returns notifications belonging to the authenticated user.

### Endpoint

```http
GET /api/notifications
```

### Query Parameters

```text
page
per_page
read
type
```

### Example

```http
GET /api/notifications?page=1&per_page=20&read=false
```

### Response

```json
{
    "success": true,
    "data": [
        {
            "id": 100,
            "type": "application_accepted",
            "title": "Application Accepted",
            "body": "Your application has been accepted.",
            "data": {
                "application_id": 15,
                "training_id": 10
            },
            "read_at": null,
            "created_at": "2026-08-07 18:30:00"
        }
    ],
    "meta": {
        "current_page": 1,
        "per_page": 20,
        "total": 1,
        "last_page": 1
    }
}
```

Only notifications belonging to the authenticated user may be returned.

---

# 2. Get Notification

Returns a single notification.

### Endpoint

```http
GET /api/notifications/{notificationId}
```

### Response

```json
{
    "success": true,
    "data": {
        "id": 100,
        "type": "application_accepted",
        "title": "Application Accepted",
        "body": "Your application has been accepted.",
        "data": {
            "application_id": 15,
            "training_id": 10
        },
        "read_at": null,
        "created_at": "2026-08-07 18:30:00"
    }
}
```

The API must verify that the notification belongs to the authenticated user.

---

# 3. Mark Notification as Read

Marks a notification as read.

### Endpoint

```http
POST /api/notifications/{notificationId}/read
```

### Response

```json
{
    "success": true,
    "message": "Notification marked as read.",
    "data": {
        "id": 100,
        "read_at": "2026-08-07 18:45:00"
    }
}
```

Only the notification owner may modify its read state.

---

# 4. Mark All Notifications as Read

Marks all unread notifications belonging to the authenticated user as read.

### Endpoint

```http
POST /api/notifications/read-all
```

### Response

```json
{
    "success": true,
    "message": "All notifications marked as read."
}
```

The operation must affect only the authenticated user's notifications.

---

# 5. Get Unread Count

Returns the number of unread notifications.

### Endpoint

```http
GET /api/notifications/unread-count
```

### Response

```json
{
    "success": true,
    "data": {
        "unread_count": 5
    }
}
```

The count should include only notifications where:

```text
read_at IS NULL
```

---

# 6. Delete Notification

Deletes or hides a notification according to the application's retention policy.

### Endpoint

```http
DELETE /api/notifications/{notificationId}
```

### Response

```json
{
    "success": true,
    "message": "Notification deleted successfully."
}
```

If soft deletion is used, the notification record should remain available for the appropriate retention period.

---

# 7. Delete All Read Notifications

Removes read notifications belonging to the authenticated user.

### Endpoint

```http
DELETE /api/notifications/read
```

### Response

```json
{
    "success": true,
    "message": "Read notifications deleted successfully."
}
```

Unread notifications must not be deleted by this endpoint.

# Notification Structure

A notification should contain enough information for the client to display the event and navigate to the relevant resource.

Recommended structure:

```json
{
    "id": 100,
    "type": "application_accepted",
    "title": "Application Accepted",
    "body": "Your application has been accepted.",
    "data": {
        "application_id": 15,
        "training_id": 10
    },
    "read_at": null,
    "created_at": "2026-08-07 18:30:00"
}
```

The `data` field should contain structured identifiers rather than embedding sensitive information into the notification body.

---

# Notification Creation

Notifications should normally be created by the server as a result of domain events.

Example:

```text
Student applies
      ↓
Application created
      ↓
Notification created
      ↓
Company receives notification
```

Another example:

```text
Company accepts application
      ↓
Application status changed
      ↓
Notification created
      ↓
Student receives notification
```

Clients must not be allowed to create arbitrary system notifications for other users.

# Read State

A notification is unread when:

```text
read_at IS NULL
```

A notification becomes read when:

```text
read_at = current server timestamp
```

The timestamp must be generated by the server.

---

# Notification Ordering

Notifications should normally be returned newest first.

Recommended ordering:

```sql
ORDER BY created_at DESC
```

When multiple notifications have the same timestamp, a deterministic secondary ordering should be used, such as the notification ID.

---

Notifications may be filtered by:



---

# Notification Privacy

Notifications may contain references to private resources.

The API must ensure that:

```text
notification.user_id
        =
authenticated_user.id
```

before returning private notification data.

A user must never be able to access another user's notification by changing the notification ID.

---

# Notification Preferences

If notification preferences are implemented, they should be managed separately from notification records.

Recommended endpoint:

```http
GET /api/notifications/preferences
```

```http
PUT /api/notifications/preferences
```

Example request:

```json
{
    "email": true,
    "in_app": true,
    "application_updates": true,
    "messages": true,
    "certificate_updates": true
}
```

The exact preference model should be introduced only if supported by the database design.

---

# Email Notifications

Some notification types may also trigger email delivery.

Recommended flow:

```text
Domain event
     ↓
Notification created
     ↓
User preferences checked
     ↓
Email queued
     ↓
Email sent
```

Email delivery should not block the main database transaction when asynchronous processing is available.

---

# Failed Email Delivery

If email delivery fails, the in-app notification should normally remain available.

Example:

```text
Notification created
       ↓
Email delivery fails
       ↓
In-app notification remains
```

Email failures should be logged according to the application's logging policy.

---

# Duplicate Notifications

The system should avoid generating duplicate notifications for the same event when the operation is retried.

Where appropriate, notifications should contain an idempotency reference such as:

```text
event_type
event_id
recipient_id
```

This can prevent accidental duplicate notifications.

---

# Idempotency

Operations that create domain events must be designed carefully so that retries do not create multiple identical notifications.

Example:

```text
Application accepted
        ↓
Notification event
        ↓
Retry
        ↓
Existing notification detected
        ↓
No duplicate notification
```

---

# Scheduled Notifications

Some notifications may be generated by cron jobs.

Examples:

```text

```

Related scheduled jobs may be found under:


# Business Flow

```text

     │
     ▼
Notification Service
     │
     ├───────────────┐
     ▼               ▼
Notification      Email
     │
     ▼
```
