## MANDATORY — component structure rules

Before creating, modifying, refactoring, or restructuring **any** frontend component, follow the conventions in:

`D:\React\React-library\docs\component-structure-rules.md`

These rules are mandatory for all frontend component work — they are the project's required component structure and organization conventions:

1. Read the structure rules when the task involves components.
2. Follow them when implementing.
3. Do not override them unless explicitly instructed to.
4. Apply them to all future component work, not just the current task.

Key rules: one job per component (fetch-and-compose vs. render-one-thing), folder-per-section with an orchestrator named after the folder with the `Container` suffix, list → dedicated item components, narrow props on leaves, server components by default with `"use client"` pushed as low as possible, sibling `constants.js` (no inline static/mock data in components), shared hooks for repeated stateful behavior, no premature promotion to `shared/` (promote-on-second-use). Forms, once wired, submit via `<form action>` + `useActionState` with uncontrolled `name`d fields (structure rules §10). Self-check checklist in section 19 of that file before presenting generated components.

**User rule — split everything, always (even UI-only):** The developer always splits long/hard-to-read components into small, single-purpose files — orchestrator + dedicated leaves — even when the work is UI-only/static-mock (no data, no wiring). Readability by splitting is not optional and does not wait for complexity to appear. This applies to every feature from the start: e.g. landing sections get `HomeHero`/`HomeFeatures`/`HomeHowItWorks`/`HomeCtaBand` each with their own leaves + sibling content constant, not one monolithic page component. Apply structure-rules §3–§7 in every interaction.

## Landmines (verified — check before touching)

- **`@/` imports are broken on `main`** — `tsconfig.json` maps `@/*` → `./src/*` (no `src/`), and `tsc --noEmit` fails. **On `dev`/`feature/auth` the alias is fixed** (`@/*` → `./*`) and typecheck passes. Never use `@/` imports on `main`; the alias is only safe on branches carrying the tsconfig fix.
- **Middleware is active** — `frontend/middleware.ts` (renamed from `proxy.ts`) exports `middleware` and runs on every request: unauthenticated users are redirected to `/sign-in` away from protected routes, public routes stay open, authenticated users are kept off auth forms, and role gating (admin → `/admin`, company → `/company`, student away from `/company` + `/admin`) is enforced. **Company-area access is role-only — approval status never gates it**: a `company` with `companyStatus === "pending"` is allowed into all `/company` routes; the status only signals which features/actions may require approval. The single remaining status rule keeps approved companies off the waiting page (`companyStatus !== "pending"` on `/company/pending-approval` → `ROLE_HOME.company`). The pending-approval route is **unauthenticated-accessible** (a fresh company has no token by design until approved) but signed-in users are gated there: only `companyStatus === "pending"` stays on it. Protected layouts (`(student)`, `company/(app)`, `admin`) call `getSession()` and redirect (`/sign-in` when unauthenticated, `ROLE_HOME[role]` on role mismatch); `company/pending-approval` renders without a session. Keep layout guards and `middleware.ts` in sync with `config/routes.ts`. **Middleware also owns access-token refresh**: when `masarJwt` is present but its `exp` has already passed (the payload is decoded without verifying the signature — expiry is the only thing the Edge runtime can check, and the backend still verifies every real request), it POSTs `auth/refresh` with the `refresh_token` + `csrf_token` cookies and the `X-CSRF-Token` header, then does **both** halves: it rewrites the request `Cookie` header via `NextResponse.next({ request: { headers } })` so the render and every `serverFetch` inside it already see the fresh token, and it persists `masarJwt`/`refresh_token`/`csrf_token` on the outgoing response. Both are required — the render must not re-present the already-revoked refresh token, and the browser must not keep it. This is why refresh lives here and not in a server render: Next makes the cookie store mutable only while a real Server Action executes (`requestStore.phase === "action"`), so a render-time refresh can rotate the token and then be unable to persist it. A **rejected** refresh (401/403: expired, revoked, or already rotated) clears all five cookies and redirects to `/sign-in?sessionExpired=1`, so a dead session is genuinely dropped instead of being re-presented forever; a **network failure** is not a rejection and leaves the session untouched, surfacing the usual "Unable to reach the server" error rather than a spurious logout. The `sessionExpired=1` force-clear runs *before* any refresh attempt, so an explicitly dead session is never revived. Cookie names and lifetimes are imported from `shared/lib/authCookies.ts` (no `server-only`/`next/headers`, so the Edge runtime can load it) — don't re-inline literals. Known limit: two *simultaneous* requests carrying the same expired token can race, and the loser's refresh is rejected (rotation is single-use), logging the user out; this is inherent to the backend's rotation semantics and was equally true before.
- **Cookie names are unified** on `masarJwt`/`masarRole`/`companyStatus`, plus the backend-minted pairs `refresh_token`/`csrf_token` — constants have a single definition in `shared/lib/authCookies.ts` (`ACCESS_TOKEN_COOKIE`, `ROLE_COOKIE`, `COMPANY_STATUS_COOKIE`, `REFRESH_TOKEN_COOKIE`, `CSRF_TOKEN_COOKIE`, `SESSION_COOKIES`, the max ages, plus `parseSetCookie`/`replaceCookiesInHeader`) — that module is framework-free so the Edge runtime can import it, and `services/cookies.ts` re-exports the names for its server-only importers. `authenticate` persists the backend-minted `refresh_token`/`csrf_token` from the login/register response so an expired access token can later be refreshed server-side, and `logout` deletes all five cookies. Read by `middleware.ts`, `services/api.ts` (`serverFetch`), and `services/auth.ts` (`getSession`). `middleware.ts` imports the same constants rather than re-declaring them: it deletes `masarRole` for a stale role cookie, writes/rotates the session on the outgoing response after a refresh, and force-clears the full session when it sees `sessionExpired=1` on an auth route.
- **`serverFetch` never refreshes — middleware owns the refresh** — `services/api.ts` is a plain request relay: it attaches `Authorization: Bearer <masarJwt>`, tolerates empty bodies, and surfaces `Set-Cookie` through `parseSetCookie` so the login flow can persist the backend-minted pair. On a **401 that carried a Bearer token** it treats the session as dead — `clearAuthCookies()` (best-effort) then `redirect()` to `/sign-in?sessionExpired=1&error=<backend message>`, where the sign-in page shows it as a toast (`SessionExpiredToast`). A 401 on a request sent **without** a token is the endpoint refusing the call itself (e.g. acting on a record the caller doesn't own) and returns the normal error envelope instead of logging anyone out; auth endpoints (`auth/*`) opt out entirely so a wrong-password 401 on login never misroutes. `redirect()` throws `NEXT_REDIRECT`, re-thrown out of the catch via `isRedirectError` so the navigation isn't swallowed as a generic error; during a Server Component render `clearAuthCookies`' deletes throw and are swallowed, and the cookies are genuinely removed by the `sessionExpired=1` middleware branch the redirect lands in. **Do not add refresh/retry logic back into `serverFetch`**: Next sets the mutable cookie phase to `action` only while a real Server Action executes, so a rotation obtained here can never be persisted during a render — and the backend has already revoked the presented refresh token by then, leaving the browser holding a dead one. See the middleware bullet for the refresh that replaced it. **HTTP failures return `status: <code>`** on the `TryCatchResponse` error path (set from the failed response's status) — consumers that need to branch on it (e.g. 404 → `notFound()`) check `res.status` instead of parsing the message. A raw-fetch network rejection (`connection refused/reset`, timeout) surfaces to callers as the stable "Unable to reach the server" message — the `/listings` route-level `error.tsx` (full-page) renders when the browse fetch throws. Cookie lifetimes (`ACCESS_TOKEN_MAX_AGE`/`REFRESH_TOKEN_MAX_AGE`) stay at 90 days — the expiry flow is tested by shortening the **backend** claim TTLs (`JWT_ACCESS_TTL`/`JWT_REFRESH_TTL` in the backend `.env`, e.g. `10`/`100`), **not** the cookie max-ages; a cookie that dies before the claim would drop the access cookie and make the refresh path unreachable. The backend still enforces its own JWT TTL.
- **`logout` is a promoted server action** living in `services/auth.ts` (a `"use server"` module) — it was promoted out of `features/auth/actions.ts` (R7) once the app-shell sidebar became a second consumer. The sidebar's `SidebarLogoutButton` calls it via `useTransition`; it notifies the backend, deletes the five session cookies, and `redirect()`s to `/sign-in`. `getSession` shares that file and stays server-only through its `services/cookies.ts` dependency.
- **`components.json` css path is stale** (`src/app/globals.css`). `npx shadcn@latest add <component>` will fail until it points at `app/globals.css`.
- `services/cookies.ts` imports `"server-only"` — cookie helpers and `getSession()` are server-side only; don't import them into client components or middleware.
- **`pnpm lint` is not configured** — ESLint 9 needs an `eslint.config.js`, which doesn't exist yet, so `pnpm lint` exits with a config error (not a code error). `tsc --noEmit` + `pnpm build` are the working verification gates.

## Architecture

- Feature-based, not role-based: `app/` is routing-only; each `features/<name>/` owns its business logic with `shared/` + role subfolders as needed. Features are empty stubs whose `index.ts` documents intended behavior. Code needed by 2+ features is promoted to `shared/`.
- **Pages are thin shells** — each `app/**/page.tsx` contains nothing but the page container: a `<main>`/grid wrapper that composes the sections (imported from feature `index.ts`). Pages own no headings, content, or layout detail beyond that container; the sections themselves carry all structure and copy.
- Route groups `(public)`, `(auth)`, `(student)` have **no URL prefix** (student is the default area); `company/` and `admin/` are real URL prefixes. Central route/permission/nav config lives in `config/` (`routes.ts` — incl. `AUTH_ROUTES_PREFIX` listing `/sign-in`, `/sign-up`, `/profile-information`, `/forgot-password`, `/verify-otp`, `/reset-password`, `/password-updated`; `permissions.ts`, `navigation.ts`).
- `services/api.ts` `apiFetch()` is the base wrapper all feature api layers go through — it attaches `Authorization: Bearer <jwt>` and tolerates empty-body responses.
- Key types in `types/`: `Role`, `Session`, `CompanyStatus`, `ApiResponse<T>`, `PaginatedResponse<T>`, `ActionState<T>`.
- **Feature types follow structure rules §14 (whole codebase migrated, incl. `public/web`):** role-specific types live in a single `features/<feature>/<role>/types.ts`, within-feature cross-role types in `<feature>/shared/types.ts` — never `types/index.ts` folders, never nested under components. Features with no role subfolders keep everything in one feature-level `types.ts` (e.g. `features/public/types.ts`; auth's small types live in `features/auth/lib/constants.ts`). Domain/shared types never live inline in component files.

## Data fetching & server/client pattern (mandatory)

**`features/listings/` is the reference implementation for every data-facing feature.** The pattern below is the default for future features unless a stated exception applies; follow listings, not this summary alone, when the summary leaves room for interpretation.

- **Read layer per role** — server-side reads live in a role-level `api.ts` (e.g. `features/listings/student/api.ts`); every call routes through `serverFetch` (or `apiFetch`) with `cache: "no-store"`, never raw browser `fetch` (backend CORS whitelist makes client calls flaky). Read functions return the `TryCatchResponse` envelope; consumers that need to branch (e.g. 404 → `notFound()`) check `res.status`.
- **Containers are async server components** — page-owning orchestrators fetch directly and compose; they throw on failure so the route's `error.tsx` renders, and branch `res.status === 404` → `notFound()`. A page shell (`app/**/page.tsx`) stays thin: unwraps params/searchParams and renders the container from the feature `index.ts`, nothing more.
- **`"use client"` pushed to interactive leaves** — only components needing interactivity/state/browser APIs get the directive, as low in the tree as possible: mutation buttons, pagination, URL-driven filter controls. Server orchestrators stay server; row/card rendering stays server with client actions isolated in dedicated leaf components (e.g. `ListingRowActions`, `DisableListingAction`).
- **Suspense scoped to data-bound regions, not whole pages** — wrap only the section that fetches in `<Suspense fallback={<SectionSkeleton />}>` (or a section-shaped skeleton); the page shell and static sections render immediately. Route-level `loading.tsx` only when the page's shape must be preserved on navigation (e.g. `(student)/listings/[id]/loading.tsx` → `DetailSkeleton`).
- **Mutations via server actions in `actions.ts`** — actions live in `"use server"` modules, POST/DELETE through `serverFetch`, and call `revalidatePath()` on success so the server-fetch pipeline re-renders fresh data (see listings save/unsave) — never client-side refetching to sync after a mutation.
- **API→UI mapping in a role-level `normalize.ts`** — raw API shapes are mapped to shared/role types in one place (e.g. `features/listings/student/lib/normalize.ts`), keeping containers clean of coercion.
- **Stated exceptions** — (1) UI-only/mock phases (like company/admin listings), before a backend exists, may use client orchestrators + a feature-local session store until integration; (2) a page that is 100% interactive CRUD with no server reads may stay client. The pattern is the default, not dogma.

## Auth feature (`features/auth/`) — conventions & state

- Auth UI (sign-in, sign-up, forgot → OTP → reset password, theme toggle) is merged into `dev` via `feature/auth`; `main` is untouched. `actions.ts` is fully wired to the backend `/api/v1/auth/*` endpoints (register, login, logout, forgot-password, verify-reset-otp, resend-reset-otp, reset-password).
- **Forms submit via `<form action>` + `useFormFeedBack`** (the `shared/hooks/useFormFeedback.ts` toast hook wrapping `useActionState` — toasts on success/error from the action's `message`/`error`, skips the untouched initial state). Server actions treat the backend as the source of truth for validation — `lib/validation.ts` keeps only the pre-request UX checks that help before a request (returning `fieldErrors`): sign-up step 1 (`validateSignupPassword`) mirrors the backend register password rules (min 12 + uppercase/lowercase/special — constants in `shared/lib/constants.ts`, matching `security.php`) plus the password/confirm-password mismatch, while the reset-password flow (`validatePasswordConfirmation`) checks the mismatch only (its backend rule differs: min 8 — stays backend-only). Every other rule is enforced by the API, whose `errors` flow back through `ActionState.fieldErrors` (rendered per-field via the shared `FieldErrorList`) plus a toast via `useFormFeedback`. Actions hit the backend and `redirect()` on success (throw-based, never returned). Two-step sign-up: step 1 (`stageSignup`) validates and redirects to `/profile-information`, carrying the basics (incl. password) in the in-memory `SignupDraftProvider` client context mounted in `app/(auth)/layout.tsx` — never a cookie/storage/URL; step 2 (`signup`) re-reads those basics from the form's hidden inputs, combines them with the profile fields, and issues exactly ONE `auth/register` call. On a rejected register, step 2 echoes the entered (non-sensitive) profile values back in `ActionState.data` (`SignupStepTwoValues`) and `ProfileInformationForm` re-seeds them via `defaultValue` — the same React-19 form-reset pattern as step 1's `SignupStepOneValues`; passwords are never echoed. Register auto-logs-in students (backend returns a token) → `ROLE_HOME`; companies get no token → `/company/pending-approval` (rendered without a session — see the middleware landmine). On login (and company register), `authenticate` derives the `companyStatus` cookie from the backend-reported `user.status` — `pending` stays `pending`, `rejected` maps to `rejected`, anything else (e.g. `active`) means approved (the backend 403s pending/rejected logins, so an authenticated company is approved by definition) — never from the role; `middleware.ts`/`getSession` use it to keep approved companies off the pending page. The `signup` action redirects companies to `/company/pending-approval` when the register response reports `userStatus === "pending"` (again status, not role). `FormAlert`/`SuccessPanel` stay deleted — feedback is toast-only.
- **Server `*Container` per flow** composes `AuthCard` + form + footer. Pages deep-import containers (`@/features/auth/components/<section>/<Section>Container`); containers are NOT exported from the feature index, forms ARE.
- **Section folders** (kebab-case, orchestrator named after the folder with the `Container` suffix): `sign-in/`, `sign-up/` (+ nested `role-selector/`, `footer/`), `profile-information/`, `forget-password/`, `verify-otp/`, `reset-password/`, `pending-approval/`, `password-updated/`. Feature-internal reuse in `components/shared/`.
- **Auth shell is shared**: `app/(auth)/layout.tsx` and `app/company/pending-approval/layout.tsx` both render `AuthPageShell` (`features/auth/shared/components/AuthPageShell.tsx`, exported from the feature index) — navy `BrandPanel` + centered card + theme toggle. Never duplicate that shell in a new layout; reuse `AuthPageShell`.
- **`/company/pending-approval` is a standalone auth-gate, not a dashboard page**: companies land there right after registering (`actions.ts` `signup` redirects on `role === "company"`) — a fresh company has no token until an admin approves, so the page renders without a session (unauthenticated-accessible, gated for signed-in users as above). It deliberately opts out of the company sidebar. The sidebar'd company layout lives in the `company/(app)` route group (all dashboard pages keep the shell; URLs are unchanged); the gate sits directly under `company/` with its own layout that renders `AuthPageShell`. Company dashboard pages must stay inside `company/(app)/`.
- **`FormField` API is fixed**: `{ name, label, type, placeholder, defaultValue? }` only — no `children`/`hint`/`error`/`autoComplete`; it owns the password eye toggle and renders `Input` with `required`. `defaultValue` exists solely to re-seed a field after a rejected submit (React 19 resets uncontrolled inputs once a form action completes — e.g. `stageSignup` echoes `SignupStepOneValues` back on the mismatch error), and is never used for password fields. `SubmitButton` uses `useFormStatus` for pending state.
- **Form field `name`s must match `lib/validation.ts`** (reset form uses `password`/`confirmPassword`, not `newPassword`, even though its label is "New password"). Field metadata (label/type/placeholder) lives in `lib/constants.ts`.
- **Profile-information lookup options route through `serverFetch`** — study fields, per-field specializations, and company industries (all active specializations) are fetched server-side via `features/auth/shared/api/lookups.ts` (`fetchStudyFields`, `fetchSpecializationsByField`, `fetchIndustries`, `cache: "no-store"`). The profile form's select options come from the three sibling client hooks `useStudyFields`/`useSpecializationOptions`/`useIndustries` (`shared/hooks/`), which check `res.error` and throw before extracting `data.study_fields`/`data.specializations`. Never fetch these cross-origin with raw browser `fetch` — the backend's CORS-origin whitelist (`config/cors.php`) makes client calls flaky (cryptic "Failed to fetch"), while `serverFetch` runs in Next's server runtime and reports real `error`/`status` (public endpoints, so no Bearer, no refresh).
- **Canonical section suffix `Container`** — a section's orchestrator is named after its folder and default-exported (e.g. `verify-otp/VerifyOtpContainer`), while its form is a named export from the feature `index.ts` (`OtpForm`, `OtpInput` lives beside it).
- **OTP step:** `OtpInput` renders `OTP_LENGTH` (6) segmented boxes with auto-advance/backspace/paste and mirrors the digits into a hidden `token` input so the surrounding form's `FormData` carries the code; `OTP_LENGTH` lives in `lib/constants.ts`. `OtpForm` (email passed via `searchParams` from `/verify-otp?email=…`) submits to `verifyOtp` → `auth/verify-reset-otp`, then redirects to `/reset-password/{token}?email=…` (the verified OTP doubles as the reset token). `ResendOtpButton` calls `resendOtp` (`auth/resend-reset-otp?email=…`) directly with `useTransition` + toasts. A successful `resetPassword` redirects to `/password-updated` (`PASSWORD_UPDATED_ROUTE` in `config/routes.ts`, in `AUTH_ROUTES_PREFIX`) — a transient post-reset landing whose client `RedirectCountdown` leaf shows the confirmation for `REDIRECT_SECONDS` (3) and then pushes to `/sign-in`; no toast is used for that success.

## Design system (source of truth: `frontend/masar-identity.html`)

- Tailwind v4 tokens defined via `@theme` in `app/globals.css`. primary = ink navy, secondary = seal gold, neutral = paper/stone.
- **Skeleton loading fills use the dedicated `--color-skeleton` token** (light: soft stone wash over the card surface; dark: `neutral-800`). The shared primitive `shared/components/ui/skeleton.tsx` applies `bg-skeleton`. The older `bg-accent` in that primitive was broken — the design system defines no `--color-accent`, so skeleton boxes rendered invisible (only their white `bg-card` wrappers showed).
- **Card elevation is a 4-tier scale, not one shadow** — `--shadow-card` (base card), `--shadow-card-md` (raised panel), `--shadow-card-lg` (`hero`), and `--shadow-lift` (the hover-only step). The old `--shadow-card-sm` was renamed to `-md` because it was actually *stronger* than the base `shadow-card` (alpha, not geometry), which made the name a lie; the four tiers now differ by geometry. Dark mode expresses the same tiers as ring strength, since a drop shadow is invisible on a near-black surface. Prefer the `shared/components/dashboard-section/` `DashboardSection` `elevation` prop (`base`/`raised`/`hero`) + `interactive` over hand-rolling a shadow onto a `bg-card` div — six dashboard sections were copy-pasting the same shell before it existed.
- **`sage` is reserved EXCLUSIVELY for the "hire opportunity confirmed" signal** — never reuse it as a generic success color. Alert/status colors (`success`/`warning`/`error`/`info`) are separate tokens.
- `paper` (neutral-100) is certificate-only. The circular seal/stamp mark signifies anything verified (approval, certificate, confirmed hire).
- **App logo = raw PNG from `design/`** — `public/logo.png` (the square seal, from design/ — note: the actual file is `logo.png`, there is no `bg-logo.png`) rendered via `BrandMark` (`features/auth/shared/components/BrandMark.tsx`) next to the `Mas<span>ar</span>` wordmark text; `app/icon.png` (a copy of the same seal) is the site favicon/browser-tab icon. Never redraw, recolor, or edit those assets. **Logo appearance rules:** the seal ALWAYS uses the primary color (the PNG's own navy — fixed in every theme, never recolored white in dark mode) and can sit on a white backing (`bg-neutral-50`) for contrast on dark/navy surfaces. That backing is **masked to the seal's own silhouette** (`mask-image: url(/logo.png)`, `mask-size: contain`) so it hugs the logo shape instead of reading as a white box beyond the image. The `chip` prop controls the backing: `"always"` (auth pages + sidebar rail, both themes) vs `"dark"` (public header/footer, white chip only in dark mode; light mode keeps the plain logo on the surface). The wordmark is `text-primary-text` on background/card surfaces and **white** (`text-neutral-50`) on the navy panel/rail via the `onDark` prop; "ar" is always `text-secondary` gold (the fixed brand seal-gold, chosen so it reads on both navy and light surfaces). Note: a `brightness(0) invert(1)` filter approach was tried and dropped the invert in real browsers — don't reintroduce it.
- IBM Plex Sans/Serif/Mono + Arabic fonts are wired in `app/layout.tsx` (Arabic ready for v2). **Dancing Script was added for the certificate signature line only** (variable `--font-dancing-script`, exposed as the `--font-signature` theme token mapped to the `font-signature` utility) — the company name on the certificate document is its sole consumer; do not repurpose it for UI text.
